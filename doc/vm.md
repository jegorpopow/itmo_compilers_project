# Виртуальная машина: архитектура и инженерные решения

Документ описывает виртуальную машину (VM) проекта целиком: её архитектуру,
модель исполнения, принятые инженерные решения и причины этих решений,
реализованные алгоритмы (включая сборщик мусора), а также тесты.

Сборка и запуск вынесены в отдельный документ — см. [`tooling.md`](tooling.md).
Формат байткода подробно описан в [`binary_format.txt`](binary_format.txt).

---

## 1. Назначение и обзор

VM — это **стековая виртуальная машина**, исполняющая байткод, который порождает
компилятор языка `¡`. Конвейер всего проекта:

```
исходник (tests/src/¡name!)  --[компилятор, Rust]-->  program.obj  --[VM, C++]-->  stdout
```

VM получает на вход бинарный `.obj`-файл, загружает его в память, находит функцию
`main` и исполняет байткод, печатая результат в стандартный вывод. VM написана на
C++23 и не зависит от компилятора в рантайме — единственный контракт между ними
это формат байткода (магия `0x494D564D`, версия `4`).

Ключевые свойства:

- стековая модель вычислений (нет регистров, все промежуточные значения на стеке);
- динамическая типизация значений на рантайме через тег-идентификатор типа;
- управление памятью кучи через трассирующий **mark-sweep** сборщик мусора;
- таблица RTTI для печати значений и инициализации массивов по умолчанию.

## 2. Высокоуровневая архитектура

Компоненты (заголовки в `vm/include/vm/`, реализация в `vm/src/vm/`):

| Компонент | Файлы | Ответственность |
|-----------|-------|-----------------|
| `Value` | `value.hpp` | Тегированное значение на стеке/в полях объектов |
| `Opcode`, под-опкоды | `opcodes.hpp` | Константы байткода |
| `Instruction`, `Program`, `FunctionRecord` | `program.hpp` | Декодированная программа |
| `Loader` | `loader.hpp`, `loader.cpp` | Чтение и разбор `.obj` |
| `RttiTable` и записи RTTI | `rtti.hpp` | Информация о типах для рантайма |
| `OpcodeHandler<>`, таблица диспетчеризации | `interpreter.hpp`, `handlers.hpp` | Обработчики опкодов |
| `Vm` | `vm.hpp`, `vm.cpp` | Состояние и главный цикл исполнения |
| `CallFrame` | `call_frame.hpp` | Кадр вызова функции |
| `HeapObject`, `GarbageCollector` | `heap.hpp`, `heap.cpp` | Куча и сборщик мусора |
| адресное кодирование | `address.hpp` | Кодирование lvalue-адресов в `Value` |
| `VmError` и наследники | `error.hpp` | Иерархия ошибок |
| CLI | `main.cpp` | Точка входа, разбор аргументов |

Граф зависимостей (упрощённо):

```
main.cpp ── Loader ── Program ── { RttiTable, Instruction, FunctionRecord }
   │
   └──────── Vm ── { eval_stack, globals, call_stack, GarbageCollector }
                 └ таблица диспетчеризации (OpcodeHandler<Opcode>) ── handlers.hpp
```

Важная деталь сборки: `handlers.hpp` подключается **только** из `vm.cpp`, после
`vm.hpp`, потому что обработчики используют полное определение `Vm`. Таблица
диспетчеризации инстанцируется именно там (см. раздел 6).

## 3. Модель значений (`Value`)

Значение — это «жирный тег» фиксированного размера **16 байт**:

```cpp
struct Value {
  uint32_t type_id = kIntegerTypeId;  // тег типа
  uint32_t aux     = 0;               // вспомогательное поле (для адресов)
  uint64_t data    = 0;               // полезная нагрузка
};
```

Интерпретация `data` зависит от `type_id`:

| `type_id` | Значение | `data` |
|-----------|----------|--------|
| `kIntegerTypeId = 0` | `integer` | `int64_t` (bit-cast) |
| `kBooleanTypeId = 1` | `boolean` | `0` / `1` |
| `kRealTypeId = 2` | `real` | `double` (bit-cast) |
| `kNullTypeId = 3` | `null` | `0` |
| `kAddressTypeId = 0xFFFFFFFF` | адрес lvalue | см. раздел 8 |
| `kVoidTypeId = 0xFFFFFFFE` | пустой тип возврата | — |
| `>= 4` (пользовательский) | ссылка на `HeapObject` | указатель (bit-cast) |

Доступ к данным — через фабрики (`makeInteger`, `makeReal`, `makeBoolean`) и
аксессоры (`asInteger`, `asReal`, `asBoolean`). Предикат `isRef()` истинен только
для ссылок на кучу (исключает все примитивы, `null`, адрес и `void`) — именно он
используется сборщиком мусора, чтобы отличать ссылки от чисел.

### Инженерные решения

- **Tagged struct, а не NaN-boxing.** Можно было упаковать всё в один `double`
  через NaN-boxing, но явный `type_id` проще, портируемее и читаемее; для учебной
  VM экономия 8 байт не стоит усложнения и UB-рисков. Тип всегда известен явно.
- **`int64_t`/`double` через `std::bit_cast`** — без union и без нарушения strict
  aliasing.
- **Поле `aux` упаковано в padding.** Изначально `Value` был `{type_id, data}` =
  16 байт (4 байта на тег + 4 байта выравнивания + 8 байт данных). Адресам нужно
  больше информации (см. раздел 8), поэтому добавлено поле `aux`. Оно сделано
  `uint32_t` и помещено **между** `type_id` и `data`, заняв те самые 4 байта
  выравнивания — поэтому `sizeof(Value)` остался **16 байт**, без роста памяти на
  каждом значении (а значений в куче и на стеке — миллионы).

## 4. Формат байткода и загрузчик

Полный формат — в `binary_format.txt`. Кратко, файл `.obj` (всё little-endian):

```
u32 magic = 0x494D564D ("IMVM")
u32 version = 4
u32 global_count
u32 rtti_table_size      + rtti_table_size  описаний типов
u32 function_table_size  + function_table_size Function Records
u32 instruction_count    + instruction_count инструкций по 16 байт
```

Каждая инструкция — 16 байт фиксированного размера:

```
[opcode:u8][subopcode:u8][arg16:u16][arg32:u32][arg64:u64]
```

`Loader::loadFromFile` (`loader.cpp`):

1. читает файл целиком в буфер;
2. проверяет магию и версию (`LoadError` при несовпадении);
3. читает `global_count`;
4. читает RTTI-таблицу: индекс записи = её `type_id`; примитивы регистрируются по
   байту типа, записи — со списком имён/типов полей, массивы — с типом элемента;
5. читает таблицу функций (`FunctionRecord`: имя, `label_id`, типы аргументов,
   тип возврата);
6. декодирует инструкции (`std::memcpy` в `Instruction`);
7. строит две индексные структуры:
   - `label_map`: `label_id → индекс инструкции` (по всем инструкциям `kLabel`);
   - `function_name_map`, `function_label_map`.

`Loader::makeTestProgram` — упрощённый конструктор `Program` из вектора инструкций
с единственной функцией `main` на метке `0`; используется юнит-тестами, чтобы не
гонять данные через бинарный формат.

### Инженерные решения

- **Инструкции фиксированного размера 16 байт** — простое декодирование (никакого
  переменного length-prefix), индексация `pc` по массиву, тривиальный `Jump`.
  Цена — перерасход места, но это не критично.
- **Метки резолвятся один раз при загрузке** в хэш-таблицу. На рантайме `Jump`/
  `Call` — это O(1) поиск, а сами инструкции `kLabel` остаются в потоке как no-op
  (упрощает кодогенерацию: не нужно патчить смещения).
- **Чтение в один буфер + проверки границ** (`ReadLE`/`readString` бросают
  `LoadError` при усечении файла) — устойчивость к битым `.obj`.

## 5. Модель исполнения

### 5.1. Состояние машины

`Vm` хранит всё состояние исполнения:

```cpp
Program                 program_;       // загруженная программа (только чтение)
std::vector<Value>      eval_stack_;    // стек вычислений (+ локальные переменные)
std::vector<Value>      globals_;       // глобальные переменные
std::vector<CallFrame>  call_stack_;    // стек кадров вызова
std::size_t             pc_;            // программный счётчик (индекс инструкции)
bool                    halted_;        // флаг останова
GarbageCollector        gc_;
std::size_t             next_gc_at_;    // адаптивный порог сборки мусора
```

Логически состояние делится на **три региона памяти** плюс счётчик:

- **`globals_`** — плоский массив глобальных переменных, размер известен из
  заголовка (`global_count`), индексируется напрямую. Живёт всё время работы.
- **`eval_stack_`** — главный рабочий регион. На нём лежат: (а) промежуточные
  значения вычислений (операнды опкодов), и (б) локальные переменные текущих
  функций. Оба вида значений сосуществуют в одном векторе (см. 5.3).
- **`call_stack_`** — стек кадров `CallFrame`. Каждый кадр хранит аргументы
  функции, точку возврата (`return_pc`) и базу своих локальных на `eval_stack_`
  (`eval_stack_base`).
- **`pc_`** — индекс текущей инструкции в `program_.instructions`.

### 5.2. Жизненный цикл инструкции и главный цикл

`Vm::run` сначала готовит верхний уровень, затем крутит цикл выборки-исполнения:

```cpp
void Vm::run() {
  // 1. Кадр <global_init> для верхнего уровня (инициализация глобалов + вызов main).
  //    Его return_pc = конец программы, eval_stack_base = 0.
  call_stack_.push_back(<global_init frame>);

  // 2. Точка входа — метка 0.
  pc_ = program_.resolveLabel(0);

  // 3. Цикл выборки-декодирования-исполнения.
  const auto& table = getDispatchTable();
  while (!halted_ && pc_ < program_.instructions.size()) {
    const Instruction& instr = program_.instructions[pc_++];  // выборка + сдвиг pc
    table[instr.opcode](*this, instr);                        // диспетчеризация
  }

  gc_.collect(*this);  // финальная сборка
}
```

Один шаг — это: прочитать `instructions[pc_]`, увеличить `pc_`, вызвать обработчик
по таблице. **`pc_` инкрементируется до вызова обработчика**, поэтому переходы
(`Jump`, `Call`, `Ret`) просто перезаписывают `pc_` своим значением — для
линейных инструкций он уже указывает на следующую.

Исполнение останавливается, когда:

- `halted_ == true` — выставляется в `Ret`, когда возвращается последний кадр
  (опустошается `call_stack_`), либо явным `Halt`;
- `pc_` вышел за пределы массива инструкций;
- брошено исключение `VmError` (см. раздел 12) — тогда цикл раскручивается до
  `main.cpp`.

### 5.3. Раскладка eval-стека: операнды + локальные

Ключевое решение — **локальные переменные функции живут на том же eval-стеке**,
начиная с позиции `eval_stack_base`, записанной в кадре. Выше них растут
временные значения вычислений. Схема на момент исполнения тела функции:

```
eval_stack_ (растёт вверх):

  индекс
  ...        ← вершина: временные операнды текущего выражения
  base+2     │ локальная переменная #2
  base+1     │ локальные переменные функции (адресуются Load/Store kLocal)
  base+0     │ локальная переменная #0
  base-1     ← ниже: временные/локальные вызывающего кадра
  ...
   0         ← дно стека

call_stack_.back().eval_stack_base = base
call_stack_.back().arguments       = [arg0, arg1, ...]   (отдельный вектор в кадре)
```

`getLocal(i)` обращается к `eval_stack_[base + i]`; если слот ещё не существует,
вектор **дорастает** (`resize`) — так лениво выделяются слоты под локальные при
первом обращении. `getArgument(i)` читает из `frame.arguments`. `getGlobal(i)` —
из `globals_`.

### 5.4. Пример трассировки

Рассмотрим вычисление `7 + 3` (под-опкод `kIntAdd`). Состояние вершины eval-стека:

| `pc_` | Инструкция | Действие | Вершина eval-стека после |
|-------|------------|----------|--------------------------|
| 0 | `IntConst 7` | push 7 | `[7]` |
| 1 | `IntConst 3` | push 3 | `[7, 3]` |
| 2 | `BinOp kIntAdd` | pop 3, pop 7, push 7+3 | `[10]` |
| 3 | `Print integer` | pop 10, печать `10\n` | `[]` |

А вот вызов функции `f(a)` (с одним аргументом), упрощённо:

1. вызывающий кладёт аргумент на стек: `[..., a]`;
2. `Call f`: VM снимает `a` в `frame.arguments`, ставит `return_pc`,
   `eval_stack_base = eval_stack_.size()`, переводит `pc_` на тело `f`;
3. тело `f` работает со своими локальными (выше `base`) и читает `a` через
   `Load kArgument 0`; результат кладёт на стек и делает `Ret`;
4. `Ret`: снимает возвращаемое значение, **усекает** `eval_stack_` до
   `eval_stack_base` (убирая все локальные/временные `f`), кладёт обратно
   возвращаемое значение и восстанавливает `pc_ = return_pc`.

Таким образом весь поток данных между инструкциями идёт через вершину eval-стека,
а вызовы аккуратно изолируют свои локальные регионы через `eval_stack_base`.

## 6. Диспетчеризация опкодов

Каждый опкод реализован специализацией шаблона:

```cpp
template <Opcode kOpcode>
struct OpcodeHandler {                     // базовый шаблон — «неизвестный опкод»
  static void execute(Vm& vm, const Instruction& instr);  // бросает RuntimeError
};

template <> struct OpcodeHandler<Opcode::kIntToBool> {
  static void execute(Vm& vm, const Instruction&) { /* ... */ }
};
```

Таблица из 256 указателей на функции строится на этапе компиляции:

```cpp
template <std::size_t... Is>
constexpr std::array<HandlerFn, 256> buildDispatchTable(std::index_sequence<Is...>) {
  return {&OpcodeHandler<static_cast<Opcode>(Is)>::execute...};
}
```

Диспетчеризация на рантайме — одно индексирование массива: `table[instr.opcode]`.

### Инженерные решения

- **Таблица указателей вместо `switch`.** O(1) переход без ветвлений на каждый
  опкод; компилятор C++ не обязан угадывать структуру `switch`. Таблица —
  `constexpr`, строится один раз при статической инициализации.
- **Параметр шаблона — `enum class Opcode`, а не `int`.** Специализации читаются
  как `OpcodeHandler<Opcode::kIntToBool>` вместо `OpcodeHandler<6>`. Это
  безопасно: у `Opcode` фиксированный базовый тип `uint8_t`, поэтому **любое**
  значение `0..255` является валидным значением enum, и `static_cast<Opcode>(Is)`
  для всех индексов корректен (не UB). Несуществующие опкоды (`0`, `32..255`)
  попадают в базовый шаблон и бросают `RuntimeError`.
- **`handlers.hpp` включается один раз из `vm.cpp`** — чтобы избежать ODR-проблем
  и чтобы все специализации были видны до инстанцирования таблицы.

Полный список опкодов — в `opcodes.hpp` (стек: `Drop/Dup/Swap`; арифметика
`BinOp/UnOp` с под-опкодами; конверсии; константы; доступ к переменным
`Load/Store/AddressOf`; косвенный доступ `LoadAddress/StoreAddress`; куча
`AllocRecord/AllocArray/AllocArrayDynamic`; массивы/поля `ArraySize/ElementAddress/
FieldAddress`; управление `Label/Jump/JumpCond/Call/Ret`; ввод-вывод `Print/Panic`).

## 7. Соглашение о вызовах

`CallFrame`:

```cpp
struct CallFrame {
  std::string        function_name;
  std::size_t        return_pc;        // куда вернуться после Ret
  std::vector<Value> arguments;        // аргументы функции
  std::size_t        eval_stack_base;  // база локальных переменных на eval-стеке
  uint32_t           return_type_id;
};
```

Вызов (`Vm::call`):

1. по `label_id` находится `FunctionRecord`, из него — число аргументов `argc`;
2. с вершины `eval_stack_` снимается `argc` значений в `frame.arguments`
   (в обратном порядке, чтобы сохранить исходный порядок аргументов);
3. `frame.return_pc = pc_` (счётчик уже указывает на инструкцию после `Call`);
4. `frame.eval_stack_base = eval_stack_.size()` — локальные переменные функции
   будут жить на eval-стеке начиная с этой позиции;
5. `pc_` переводится на тело функции.

Возврат (`Vm::ret`):

1. снимается верхний кадр;
2. снимается возвращаемое значение, eval-стек **усекается** до `eval_stack_base`
   (выбрасываются все локальные/временные), затем кладётся возвращаемое значение;
3. `pc_ = frame.return_pc`; если стек кадров опустел — `halted_ = true`.

Доступ к переменным (`getVariable`):

- **глобальные** — индекс в `globals_` (с проверкой границ);
- **локальные** — `eval_stack_[eval_stack_base + index]`; если индекс выходит за
  текущий размер, eval-стек **дорастает** (`resize`) — это лениво аллоцирует слоты
  под локальные;
- **аргументы** — индекс в `frame.arguments`.

### Инженерные решения

- **Локальные живут прямо на eval-стеке** (а не в отдельном векторе) — экономия и
  простота: один регион памяти, корни GC сканируются единообразно, при `Ret`
  локальные снимаются одним `resize`.
- **Метод `Vm::ret`, а не `return`** — слово `return` зарезервировано в C++.
- **Кадр `<global_init>`** даёт единообразие: верхний уровень исполняется как
  «функция» с `return_pc`, указывающим за конец программы.

## 8. Адреса (lvalue) и косвенный доступ

Операции `AddressOf`, `FieldAddress`, `ElementAddress` кладут на стек **адрес** —
ссылку на ячейку, в которую затем пишут (`StoreAddress`) или из которой читают
(`LoadAddress`). Адрес бывает двух видов:

- **адрес переменной** (глобал/локал/аргумент);
- **адрес поля кучи** (поле записи или элемент массива внутри `HeapObject`).

Адрес кодируется **прямо внутри `Value`**, без аллокаций (`address.hpp`):

```cpp
// type_id == kAddressTypeId всегда
// младший бит aux — флаг «адрес поля кучи»
// адрес переменной:  aux = 0;              data = (loc_kind << 16) | var_index
// адрес поля кучи:   aux = (idx << 1) | 1; data = HeapObject*
```

`loadAddress`/`storeAddress` декодируют это и читают/пишут нужную ячейку.

### Инженерное решение — почему inline-кодирование (важно!)

Изначально адреса хранились в отдельном пуле `AddressPool` как объекты
`AddressDescriptor`, размещённые в куче через `std::make_unique`, а ссылка на
дескриптор клалась в `Value`. Освобождались они только во время сборки мусора.

Профилирование рейтрейсера выявило, что это **главное узкое место**:

- каждое обращение к полю/элементу (`lhs.x`, `c.pixels[i]`, ...) делало
  аллокацию в куче;
- рейтрейсер выполняет ~37 таких обращений на одну аллокацию объекта → миллионы
  `malloc`/`free`, и пул разрастался до сотен тысяч записей;
- на сцене 120×160 это давало ~35% времени в GC и кратный перерасход памяти.

Решение — кодировать адрес **в самих 16 байтах `Value`**:

- для адреса поля кучи нужны указатель (64 бита) + индекс поля + флаг — не влезает
  в одно поле `data`, поэтому добавлено `aux` (упакованное в padding, см. раздел 3,
  размер `Value` не вырос);
- индекс поля кодируется как `(idx << 1) | флаг` в `uint32_t` — этого хватает на
  любые реальные массивы;
- адрес переменной кодируется тривиально в `data`.

Эффект: пул и вся аллокация под адреса **исчезли** полностью. На рейтрейсере это
дало кратное ускорение и снижение памяти ещё до учёта GC (см. раздел 14).

Ограничение/предположение: адреса считаются **транзиентными** — они живут только
на eval-стеке между созданием и потреблением. Это согласуется с тем, как их
порождает компилятор, и с тем, как их видит сборщик мусора (см. раздел 10).

## 9. Куча и объекты

```cpp
enum class HeapObjectKind : uint8_t { kRecord, kArray };

struct HeapObject {
  uint32_t           type_id;
  HeapObjectKind     kind;
  std::vector<Value> fields;   // поля записи или элементы массива
  bool               marked;   // бит пометки GC
};
```

- **Записи и массивы — один тип `HeapObject`**, различаются по `kind`. Поля и
  элементы хранятся в общем `std::vector<Value>`.
- **Массивы 1-based**: язык индексирует массивы с единицы, поэтому `elementAt`
  принимает «языковой» индекс и вычитает 1 (с проверкой границ →
  `IndexOutOfBoundsError`).
- **Инициализация по умолчанию**: при `allocArray` через RTTI определяется тип
  элемента, и массив примитивов заполняется типизированным нулём (`0`, `0.0`,
  `false`); массивы ссылок заполняются `null`.

## 10. Сборщик мусора — алгоритмы

`GarbageCollector` (`heap.cpp`) реализует классический **трассирующий
mark-sweep**, **неперемещающий** (non-moving), **stop-the-world**.

### 10.1. Структуры данных и инварианты

- `std::vector<HeapObject*> objects_` — список всех объектов, которыми владеет
  сборщик. Каждый объект создаётся через `new` в `allocate(...)` и сразу
  добавляется в `objects_`; удаляется через `delete` в фазе sweep.
- бит `HeapObject::marked` — служебная пометка трассировки.

Инварианты:

- **Между сборками `marked == false` у всех объектов.** Бит используется только
  внутри одного цикла `collect` и сбрасывается в конце sweep (см. 10.3). Поэтому
  следующий цикл стартует с чистого состояния — отдельный «unmark»-проход не нужен.
- **Указатели стабильны**: объект не перемещается за всю жизнь, поэтому «сырой»
  указатель в `Value.data` и указатель внутрь `fields` (в адресе поля кучи)
  остаются валидными.

`collect(vm)` целиком:

```cpp
void GarbageCollector::collect(Vm& vm) {
  mark(vm);    // 1. пометить всё достижимое от корней
  sweep();     // 2. удалить непомеченное, снять биты
}
```

### 10.2. Фаза Mark — трассировка от корней

Корневое множество (`GarbageCollector::mark`) — это всё, откуда программа может
напрямую дотянуться до объектов:

1. **глобальные переменные** (`globals_`);
2. **аргументы всех кадров** вызова (`call_stack_[*].arguments`);
3. **весь eval-стек** — это покрывает и промежуточные значения, и локальные
   переменные (они живут на eval-стеке, см. 5.3);
4. **адреса полей кучи, лежащие на eval-стеке** — особый случай: значение-адрес
   само не является ссылкой (`isRef()` для него ложно), но оно указывает внутрь
   объекта, и этот объект надо удержать.

Псевдокод:

```cpp
void mark(Vm& vm) {
  for (v : vm.globals())                 markValue(v);
  for (frame : vm.call_stack())
    for (v : frame.arguments)            markValue(v);
  for (v : vm.eval_stack())              markValue(v);

  // адреса полей кучи на стеке: удерживаем объект-владелец
  for (v : vm.eval_stack())
    if (v.isAddress() && isHeapFieldAddress(v) && heapFieldObject(v))
      markObject(heapFieldObject(v));
}

void markValue(const Value& v) {
  if (!v.isRef()) return;                // только ссылки на кучу
  if (auto* obj = bit_cast<HeapObject*>(v.data)) markObject(obj);
}

void markObject(HeapObject* obj) {
  if (!obj || obj->marked) return;       // защита от циклов и повторов
  obj->marked = true;
  for (const Value& field : obj->fields) markValue(field);  // рекурсивный DFS
}
```

Зачем нужен пункт 4: между `FieldAddress`/`ElementAddress` (получили адрес
ячейки) и `StoreAddress` (записали в неё) компилятор вычисляет правую часть
присваивания, которая может аллоцировать и **запустить сборку**. В этот момент
объект-владелец ячейки может быть достижим только через адрес на стеке — без
пункта 4 он был бы ошибочно собран, и последующая запись пошла бы по «висячему»
указателю.

**Обнаружение циклов** обеспечивает проверка `obj->marked` в начале
`markObject`: повторно в уже помеченный объект не заходим, поэтому
самоссылающаяся запись (`x.self := x`) трассируется без зацикливания.

### 10.3. Фаза Sweep — линейная очистка

`sweep` проходит `objects_` ровно один раз и одновременно сбрасывает биты:

```cpp
void sweep() {
  std::vector<HeapObject*> live;
  for (HeapObject* obj : objects_) {
    if (obj->marked) {
      obj->marked = false;     // сброс к следующему циклу (поддержка инварианта)
      live.push_back(obj);     // выживший
    } else {
      delete obj;              // мусор
    }
  }
  objects_ = std::move(live);
}
```

Стоимость фазы — O(числа объектов в `objects_` на момент сборки) = живые + мусор,
накопленный с прошлой сборки.

### 10.4. Адаптивный триггер сборки

Сборка запускается **не по фиксированному счётчику** аллокаций, а
**пропорционально размеру живого набора** (`Vm::maybeCollect`, вызывается перед
каждой аллокацией в `allocRecord`/`allocArray`):

```cpp
void Vm::maybeCollect() {
  if (gc_.objectCount() < next_gc_at_) return;        // ещё не пора
  gc_.collect(*this);
  std::size_t live = gc_.objectCount();               // после сборки = живые
  next_gc_at_ = std::max(kMinGcThreshold, live * 2);  // «удвоение кучи»
}
```

То есть после каждой сборки порог следующей ставится в **2× от числа выживших**
(но не меньше `kMinGcThreshold = 10000`). Иначе говоря, программе позволяется
аллоцировать примерно столько же объектов, сколько сейчас живёт, прежде чем
снова собирать.

**Почему это важно (амортизация).** Пусть живой набор — `L` объектов. Один цикл
`collect` стоит ≈ O(`L` + мусор). При **фиксированном** интервале `k` сборок (как
было раньше, `k = 10000`) на каждые `k` аллокаций выполняется полный обход `L`
живых, то есть суммарная работа ≈ `(N / k) · L` на `N` аллокаций — при большом
`L` это квадратично-подобно. При **удвоении кучи** между сборками успевает
аллоцироваться ≈ `L` объектов, значит сборок ≈ `N / L`, и суммарная работа
≈ `(N / L) · L = O(N)` — **амортизированно линейно** по числу аллокаций,
независимо от размера живого набора.

Пример на рейтрейсере (холст держит сотни тысяч пиксельных записей живыми):
переход с фиксированного интервала на адаптивный снизил время в GC на сцене
360×480 примерно с **15 c до ~0.2 c** (в Release-сборке). Цена — пиковая память
до ~2× живого набора (компромисс время/память, см. раздел 16).

### Инженерные решения и компромиссы

- **Почему mark-sweep, а не подсчёт ссылок?** Подсчёт ссылок не собирает циклы
  (а язык их допускает: запись может ссылаться на себя), и требует атомарных
  операций на каждом присваивании. Mark-sweep корректно собирает циклы и проще.
- **Неперемещающий GC** — указатели на `HeapObject` стабильны на всё время жизни
  объекта. Это критично: на eval-стеке лежат «сырые» указатели (в `Value.data`),
  и адреса полей кучи указывают внутрь `fields` объекта; перемещение всё бы
  поломало. Цена — фрагментация кучи (отдаём её системному аллокатору).
- **Адаптивный порог (heap-doubling)** вместо фиксированного интервала — даёт
  амортизированно линейную работу GC при большом живом наборе (обоснование и
  цифры — в 10.4).
- **Известные ограничения**:
  - рекурсивный `markObject` может переполнить стек на очень глубоких структурах
    (потенциальное улучшение — явный рабочий стек / итеративная трассировка);
  - нет финализаторов и слабых ссылок;
  - предполагается, что адреса встречаются только на eval-стеке (см. раздел 8).

## 11. Алгоритмы в VM (помимо GC)

- **Разрешение меток** — O(1) через `label_map` (хэш-таблица), построенную при
  загрузке; `Jump`/`Call` не сканируют код.
- **Диспетчеризация** — O(1) через таблицу указателей (раздел 6).
- **Форматирование `real`** (`detail::formatReal`) — нетривиально, чтобы вывод
  совпадал с эталонными golden-файлами:
  - `±inf` → `+Infinity` / `-Infinity`, `nan` → `NaN`;
  - научная запись с отрицательной экспонентой (`1e-14`) разворачивается в
    десятичную (`0.00000000000001`) с обрезкой хвостовых нулей;
  - целые `real` получают суффикс `.0` (например, `11` → `11.0`).
- **Печать значений** (`detail::printValue`/`printObject`) — рекурсивный обход с
  **обнаружением циклов**: ведётся стек «предков» (`ancestors`); если объект уже
  встречался выше по цепочке, печатается `/* repeated N levels above */` вместо
  бесконечной рекурсии. Поля записей печатаются **отсортированными по имени**
  (детерминированный вывод); имена с апострофом берутся в кавычки; массивы
  печатаются как `[ e1, e2, ]`, записи — `{ name: value, }`.
- **Преобразования типов**: `RealToInt` — **усечение к нулю** (`std::trunc`, с
  обработкой `NaN` → `ConversionError` и клиппингом `±inf` к границам `int64`);
  `IntToBool` — `i != 0`; `IntToReal`, `BoolToInt` — прямые касты.
- **Целочисленные деление и остаток** — с проверкой деления на ноль
  (`DivisionByZeroError`).

## 12. Обработка ошибок

Иерархия исключений (`error.hpp`):

```
std::runtime_error
└── VmError
    ├── RuntimeError
    │   ├── TypeMismatchError       (неверный тип на стеке)
    │   ├── StackError              (пустой стек)
    │   ├── NullReferenceError      (разыменование null)
    │   ├── IndexOutOfBoundsError   (выход за границы массива/поля)
    │   ├── DivisionByZeroError
    │   ├── ConversionError         (например, RealToInt от NaN)
    │   └── PanicError              (инструкция Panic, несёт код)
    └── LoadError                   (битый/некорректный .obj)
```

`main.cpp` ловит их раздельно и возвращает коды: успешный прогон — `0`; любая
`VmError` (загрузка/паника/рантайм) — `1`; отсутствие обязательного `-i` — `2`.

### Инженерное решение

Иерархия исключений вместо кодов ошибок: ошибки рантайма редки и фатальны для
программы, исключения дают чистый код горячего пути (обработчики опкодов не
проверяют коды возврата) и точную диагностику.

### Golden-тесты (end-to-end), `run_golden_tests.py`

Прогоняют **весь конвейер**: компилируют каждую программу из `tests/src/`, у
которой есть эталон `tests/run/pass/<name>.stdout`, исполняют её на VM и сравнивают
вывод побайтно. Скрипт сам находит бинарь компилятора и VM. Это основная защита от

и т.д.).

## 14. Производительность и память

Две оптимизации, сделанные по результатам профилирования рейтрейсера:

1. **Inline-кодирование адресов** (раздел 8) — устранило миллионы аллокаций в
   куче и неограниченный рост пула адресов.
2. **Адаптивный триггер GC** (раздел 10) — сделало работу сборщика амортизированно
   линейной при большом живом наборе.

Но **решающий фактор — тип сборки**. Debug-сборка VM компилируется с `-O0` и
`_GLIBCXX_DEBUG` (все обращения к `std::vector` проверяются на границы), что
замедляет исполнение примерно в **70 раз**. Для реальных запусков нужно
использовать **Release**.

Измеренное масштабирование рейтрейсера на Release-сборке (линейно по числу
пикселей):

| Разрешение | Пиксели | Время | Пиковая память |
|------------|---------|-------|----------------|
| 360 × 480 | 172 800 | ~2 c | ~37 MB |
| 720p (1280 × 720) | 921 600 | ~12 c | ~184 MB |
| 4K (3840 × 2160) | 8 294 400 | ~2 мин | ~1.5 GB |

Память определяется в основном живым холстом (он держит каждый пиксель-запись на
протяжении всего рендера) плюс ~2× запас от адаптивного GC.

## 16. Известные ограничения и направления развития

- **Рекурсивная фаза mark** — потенциальное переполнение стека на очень глубоких
  объектных графах; решается переходом на явный рабочий стек.
- **Неперемещающий GC** — фрагментация кучи; перемещающий/копирующий сборщик
  потребовал бы отказа от «сырых» указателей в `Value` и таблицы перемещений.
- **Адреса только на eval-стеке** — модель опирается на транзиентность адресов;
  если язык начнёт хранить адреса в переменных/полях, сканирование корней нужно
  будет расширить.
- **Таблица диспетчеризации фиксирована на 256 опкодов** — естественное следствие
  однобайтового опкода; расширение потребует второго байта/префикса.
- **Адаптивный коэффициент GC = 2×** — компромисс время/память; для очень больших
  сцен его можно уменьшить (в Release сборщик дешёвый, и более частые сборки почти
  не бьют по времени, но экономят память).
```
